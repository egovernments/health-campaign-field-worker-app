Multi-Hierarchy Support

Moving hierarchyType from build-time .env into per-project runtime, so one APK can serve users whose projects use different hierarchies.

Current approach

  • HIERARCHY_TYPE is read once from .env at app startup and pushed into DigitDataModelSingleton.
  • The same value is used for every boundary fetch, every MDMS module key, and every localization key — across the whole app lifetime.
  • To support a different hierarchy, you rebuild the APK with a different .env.
  • Some hierarchy-keyed calls (splash, language selection, login) fire before the user picks a project — they have no choice, since hierarchy is baked in.

One APK = one hierarchy. Switching means a new build.

New approach

  • Each project carries its own hierarchyType inside Project.additionalDetails (server-populated).
  • On project selection, the app reads that value and pushes it into the singleton — then all downstream calls (boundary, MDMS, localization, hierarchy-scoped APIs) use it.
  • If the project's payload doesn't include hierarchyType, fall back to the .env value. Env is a missing-field safety net, nothing else.
  • Any hierarchy-keyed call that today runs before project selection is moved to run after it. Pre-selection hierarchy work is not patched with an env read — it's relocated.
  • Switching hierarchy = logout → re-login → pick a different project. No mid-session switching.
  • On logout, cached boundaries and MDMS modules are cleared so the next login starts clean.

What needs to be thought of

  • Server payload. Backend has to actually return hierarchyType inside Project.additionalDetails. Until that ships, every project falls back to env — which is fine, but means we can't validate the runtime path end-to-end.
  • Pre-selection audit. Find every hierarchy-keyed call that runs before project selection today (splash, language pick, login, boot blocs) and confirm each can be relocated without breaking that flow. If a screen genuinely needs hierarchy before login, that's a design problem to surface now, not later.
  • Boundary cache shape. Today the boundary table is global. If a user logs into Project A (ADMIN) then logs out and into Project B (HEALTH), stale ADMIN rows must not leak. Decision: clear the table on logout (simplest), or add a hierarchyType column and filter on read.
  • MDMS / localization keys. Module keys like hcm-boundary-{hierarchy} are built at several call sites that read envConfig.variables.hierarchyType directly. Each needs to route through a single resolver instead.
  • Persistence across cold start. If the user kills and relaunches the app without logging out, the resolved hierarchy needs to survive. Persist to secure prefs, or force a re-resolve from the persisted selected-project state.
  • API calls audit. Anything else that sends hierarchyType as a query param, header, or body field — project-staff search, facility search, master-data fetches — has to go through the resolver too. One-time grep job.
  • Logout cleanup. What exactly gets wiped on logout? Boundary table, MDMS module cache, persisted hierarchyType, anything else keyed by hierarchy. List it before implementing so nothing is missed.
  • Debug guard. The resolver should assert in debug builds if it's called before project selection. Catches regressions where someone adds a new pre-selection call site without realizing.
  • Sequencing. This work ships before the single-APK refactor. Once merged, the single-APK plan can drop HIERARCHY_TYPE from its env-migration list and treat it as already runtime-sourced.
